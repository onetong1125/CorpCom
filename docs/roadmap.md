## 目标与当前基线

一个研究目标对应一个持久 Workspace，保存会话、偏好、证据和产物，支持之后继续研究。目标是让同一 Workspace 下多个 Thread 同时研究，共用一个可复用的 Docker 容器和工作区文件，由 RunCoordinator 管理各轮执行。当前已接入共享容器、文件工具和 RunCoordinator；API 已开放同 Workspace 不同 Thread 并发，整体最多同时执行两轮。M4 后端协调、M5 前端并发交互与 M6 真实双研究完整链路均已验收，包括运行中上传、文件互读、失败隔离、刷新与重启续聊。

本次需求与依赖依据会话[参考 RunCoordinator 管理运行状态](thread://01a186c0-6304-7de0-9083-915dd04103b7?hostId=local)的最新总结更新。新的 Thread 级并发方案替代原先的同 Workspace 互斥目标；容器复用与文件协作成为开放并发前的依赖。Multi-agent 保留在 11 月后续阶段，多个 Thread 同时运行不等于已实现 Multi-agent。

Jinja2 负责模板组合，YAML 负责默认配置，运行时上下文负责注入当前研究资料；仅完成模板渲染不能算上下文管理完成。

协调器的执行链路：接收请求 → 获取整体额度 → Thread 级准入并登记 running → 调用 Agent → 同一事务保存回答与 succeeded → 释放额度。异常记录 failed 并重新抛出；启动时将遗留 running 标记为 interrupted。threads 表保存最近一轮状态，由现有 Thread 查询接口返回；Checkpoint 保存框架执行历史。流式接入后再传递执行事件。

不把完整业务 Run 历史或独立版本管理设为前置条件，运行状态存储应满足 Thread 级查询与重启识别。现有工具日志中的 run_id、Python 执行目录与协调器的运行状态分别承担自己的职责。首版不包含任务排队、取消、自动重试、steering 或分布式运行协调。

## 共享执行与文件协作边界

- **容器生命周期**：首次执行创建并启动，后续复用；单进程内并发首次调用不重复创建。首版由开发者在研究请求结束并停止后端后手动停止／删除容器，暂不自动空闲停止或清理；后续调用启动已停止的容器，或重建已删除的容器。CPU、内存限制作用于整个 Workspace 容器，各 Thread 共用额度。
- **进程与文件**：共享容器内各次 Bash（包括其启动的 Python 程序）执行使用独立进程，变量不跨调用保留，文件与容器内依赖共享。旧 execute_python 仍使用独立容器及临时目录。Workspace 文件挂载到宿主机持久目录；正式依赖由 Dockerfile.sandbox 维护并随镜像提供，更新镜像后需删除旧容器再创建；运行时临时安装的依赖不保证恢复，/tmp 内容在停止或删除后不保留。
- **命令失败与超时**：返回退出码和输出；GNU timeout 到期向命令进程组发送 KILL，--init 回收孤儿进程；已验证不影响另一条并行命令或共享容器。该范围不覆盖主动脱离进程组的进程，API 的 Thread 并发由协调器控制，真实双研究已通过 M6 验收。
- **资料发现与任务目录**：Agent 用 Bash 浏览、搜索、读取文件及执行程序；文本创建和修改使用 write_file/edit_file，不用重定向、heredoc、sed -i 或临时脚本代替。代码、中间数据和报告放在 tasks/<任务名>/ 下；任务目录是组织约定，不是访问隔离。完整文件索引不再注入 context，read_file(artifact_id) 暂停注册。
- **带锁文件工具**：单进程内同一解析后路径使用同一把锁，Write 和 Edit 共用；Edit 在锁内完成“读取最新内容 → 匹配旧片段 → 替换 → 写回”。默认唯一匹配，replace_all=True 时替换全部匹配；匹配失败明确返回错误。锁不覆盖整个研究过程，Bash 或外部程序直接写文件不受保护。
- **研究中上传**：上传完成后文件进入持久 Workspace，后续工具调用可发现并读取；不要求自动注入已经开始的模型调用或 Python 进程。
- **产物衔接**：直接写入工作区的交付文件由 register_artifact 原地登记，不复制；同一路径重复登记复用 ID 和分类，后续编辑展示最新内容。旧 execute_python 的 outputs 继续自动复制归档登记，上传文件也已登记，无需再次主动登记。登记不提供历史快照。
- **暂不引入**：LiveFS、内容版本检查、自动合并或全面的强一致性保证。

## 当前实现顺序与依赖

主依赖链：**M1 容器复用 → M2 Bash → M3 文件工具与产物衔接 → M4 Thread 协调器 → M5 前端并发与上传 → M6 完整并发验收**。

这是落地顺序，不是按模块分类的顺序。M1—M3 期间保留现有 Workspace 互斥；到 M4 由 Thread 级准入替换，M5 再开放页面并发操作。
