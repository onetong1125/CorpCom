| 提示词与上下文基础 | 系统提示词内联组装，每轮注入 Workspace 信息和资料索引，checkpoint 恢复会话历史；尚未实现本轮计划的模板与上下文预算管理 |

## 已确认方向与建议的首版范围

| 优先级 | 需求 | 已确认方向 | 建议的最小范围与验收标准 |
| --- | --- | --- | --- |
| P0 | 执行协调器 | Agent 状态指运行执行状态，由协调器管理 | 统一请求准入、开始、运行、成功/失败、保存与占用释放；刷新可查询状态，服务重启后中断任务不会一直显示运行中 |
| P0 | 并发控制 | 与协调器一起设计 | 首版面向单进程部署；同 Workspace 互斥，不同 Workspace 有执行上限，超限明确拒绝；异常后释放占用 |
| P0 | 流式响应 | 前后端贯通执行过程与回答增量 | 文本增量、工具开始/结束、成功/失败可见；最终回答仅保存一次，刷新可读；明确断连后执行和保存的语义 |
| P1 | 提示词与上下文管理 | Jinja2 模板组合 + YAML 默认配置 + 运行时上下文注入，作为同一项工作推进 | 分离固定规则与动态内容；明确本轮注入的历史、工具结果、资料和记忆；选择一种上下文预算处理策略，长对话处理不破坏工具调用关系 |
| P1 | 最小记忆 | 需要跨会话承接研究，具体内容与更新规则待确认 | 建议保存 Workspace 研究摘要（当前判断、证据 Artifact 引用、待验证问题），复用已有显式偏好；验证新会话使用、更新及 Workspace 隔离，摘要不替代原始证据 |
| P0 | 全流程验收与交付 | 验收与演示保留独立时间 | 页面发起真实研究、工具取数、来源可追溯、产物保存、重新打开后续聊；补齐文档和已知限制 |
| 11 月 | Multi-agent | 已确认移至 11 月 | 按实际研究分工明确委派、子 Agent 上下文、并发、结果汇总与部分失败处理；与单 Agent 使用相同案例比较 |

Jinja2 负责模板组合，YAML 负责默认配置，运行时上下文负责注入当前研究资料；仅完成模板渲染不能算上下文管理完成。

协调器的建议执行链路：接收请求 → 并发准入 → 标记运行 → 调用 Agent → 传递事件 → 保存结果 → 更新终态 → 释放占用。状态保存方式、具体状态集合及接口在开发前确定。checkpoint 是框架执行历史，不直接代替可查询的运行状态。

不把业务 Run 表、独立版本管理或重试框架设为本轮前置条件。现有工具日志中的 run_id、Python 执行目录与协调器的运行状态应分别说明职责。任务排队、取消、自动重试和多进程并发控制暂不纳入建议首版；需要时另行确认范围。

## 进度与调整规则

- 状态使用“已验收、已实现待验收、进行中、待推进、阻塞”，注明用户确认、代码、脚本测试或真实模型验收等证据来源；不按提交数量推算完成度。
- 10/28 结束检查协调器和流式是否验收通过。未通过时，列出实际剩余工作和工时影响，再确认缩小上下文/记忆范围或延期，不自动删除需求。
- 保留 10/31 的验收收尾时间。学习与实现超时计入实际消耗，不用计划工时冒充进度。
- 自动测试、替身 Agent 的界面联调与真实模型/Docker/数据接口验收分别记录；历史成功不等于当前版本已重新验收。
- 本轮已确定 Multi-agent 移至 11 月；新闻与定时任务未纳入这 25 小时预算，具体后续排期尚未确认。

## 开发前待明确

1. 协调器状态保存方式，以及断连、服务重启后的状态语义。
2. 不同 Workspace 的并发上限与配置位置。
3. 上下文预算及历史处理策略。
4. 研究记忆的内容、写入触发方式与更新规则。

上述待定项应在对应小批次开始时明确，形成可验收的实现边界。后端仍按“解释一小步 → 用户实现 → 检查 → 验证”推进。
